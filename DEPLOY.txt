WHERE THINGS ARE
================

  site/           the production build. Root-absolute paths, indexable,
                  CNAME included. For the real domain. This is also what
                  `node build.js` writes and what you serve locally.

  dist/preview/   the preview build. Use this one on GitHub Pages.

  src/ public/ scripts/ build.js      source.


THE PREVIEW BUILD
=================

It uses RELATIVE paths (./assets/... , ../../assets/... , computed from
each page's own depth), so it works no matter where you put it:

    norvixhq.github.io/                    works
    norvixhq.github.io/norvixco.com/       works
    any other repo name                    works
    a subfolder on any host                works

You do not have to tell it the repo name. That removes the mistake that
made the first attempt render as a blank loader: a build expecting one
base path served from another, so every asset 404'd.

It is also deliberately not indexable:
  · <meta name="robots" content="noindex, nofollow"> on every page
  · robots.txt -> Disallow: /
  · no CNAME
Leave that alone while previewing, so the preview cannot get indexed and
later compete with the real site for the same content.

DEPLOY: push the CONTENTS of dist/preview/ to the repo that serves your
Pages URL — repo root, or /docs, per your Pages setting. .nojekyll is
included; Pages will not serve an /assets folder without it.


SERVING site/ LOCALLY
=====================

  cd site
  python3 -m http.server 8000

From INSIDE site/. One level too high and every asset 404s.


REBUILDING
==========

  node build.js
      -> site/   production

  RELATIVE=1 PREVIEW=1 PREVIEW_ORIGIN=https://norvixhq.github.io node build.js
      -> site/   preview. Copy it to dist/preview/, then run the plain
         build again so site/ is production once more.


IF A PAGE EVER LOOKS UNSTYLED
=============================

The loader now clears itself after 4 seconds with CSS alone, so a missing
asset can no longer leave you stuck on a blank screen. If a page renders
but looks plain, open /assets/site.css directly in the browser. A 404
there means the build and the serving location disagree — use the
relative build and it cannot happen.
